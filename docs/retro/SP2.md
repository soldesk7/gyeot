## 요약 (먼저 읽을 것)

- **스프린트 목표 달성.** 사진을 올리면 인식 결과가 화면에 출력되고 지도에 실제 응급실이 거리순으로 표시되는 것을 확인하였다. 홈·업로드·확인·가이드·지도·고지 여섯 화면이 모두 이어졌다.
- **SP3 작업을 두 건 당겨왔다.** 응급실 목록 캐싱과 실시간 가용병상 조합이다. 응답 시간이 약 7초에서 0.01초대로 줄었고, 병상 수까지 응답에 담긴다.

- 공공데이터 **일일 트래픽을 소진**해 반나절 개발이 막혔다. 원인은 코드가 아니라 설정값이었다.

## 2. 목표 달성 여부 (3줄 이상)

**목표는 달성했다.** "업로드→인식→확인까지 실제 데이터로 잇는다"가 이번 주 목표였고, 사진을 올리면 Gemini 인식 결과가 화면 B에 표시되기까지 실제로 이어진다. 여기에 지도까지 실데이터로 붙어 계획보다 앞서 있다.

**계획보다 앞선 이유는 응급실 API가 예상보다 빨리 끝났기 때문이다.** SP1 회고에서 "SP2가 일찍 끝나면 병상 캐싱을 앞당긴다"고 적어둔 대로 진행했다. 결과적으로 SP3에 몰려 있던 T 작업 중 둘이 빠져 SP3에 콘텐츠 API를 넣을 여유가 생겼다.

**다만 F-04(응급처치 가이드)는 통째로 남았다.** 화면 C가 아직 화면 안에 콘텐츠를 하드코딩한 상태이고 콘텐츠 API도 없다. 이 상태로 시연하면 불변 원칙 2(임의 콘텐츠 저작 금지, 공식 기관 자료만 연결)를 어긴 화면을 보여주게 된다. SP3의 가장 큰 덩어리다.

## 3. 막힌 것 (3줄 이상)

**콘텐츠를 그대로 사용할 수 없다는 것이 확인됐다.** 이용조건을 검수하다 확인했다. 단계별 텍스트의 출처인 질병관리청 국가건강정보포털은 **공공누리 제4유형**(출처표시 + 비상업적 이용만 + **변경금지**)이라 원문을 수정할 수 없는데 수집된 텍스트는 원문을 다듬어 새로 쓴 상태였다. 화상 텍스트를 원문과 대조해 보니 10개 항목 중 **6개가 그 페이지에 없는 내용**이었고, 시트에는 출처가 질병관리청 하나로만 적혀 있었다. 출처를 확인할 수 없는 처치 문구가 섞여 있다는 뜻이라 불변 원칙 2에 직접 걸린다.

**대안으로 생각했던 경로도 막혔다.** 소방청 생활안전정보는 제1유형이라 다듬어 써도 되는데, 확인해 보니 **단계별 텍스트가 아니라 인포그래픽 이미지 한 장**이었다. 텍스트를 소방청 자료로 대체할 수 없다. 결국 제4유형 원문을 문장 단위로 그대로 옮기는 방식으로 정리해야 한다. 다행히 복제는 모든 유형에서 허용되므로 문장을 고치지만 않으면 된다.

**공공데이터 일일 트래픽을 소진했다.** 캐시 갱신 주기를 확인하려고 `refresh-ms`를 100ms로 줄여 두고 되돌리지 않은 채 방치한 것이 원인이다. 7초짜리 조회를 0.1초 간격으로 반복하는 상태가 되어 하루치 한도를 모두 소모했고 `429 API token quota exceeded`가 떠서 반나절 개발과 검증이 막혔다. 코드 문제가 아니라 설정값 문제였는데 증상만 봐서는 인증 문제로 오해하기 쉬웠다.

**금요일 데모가 무산됐다.** 학교 정전으로 모이지 못해 08-03(월)로 연기했다. F3은 작업과 리뷰를 마쳤으나 PR을 올리기 전에 해산해 월요일에 머지했다.

### 트러블슈팅 기록

- 응급실 조회 결과가 시간대에 따라 변동 — 트러블슈팅 문서(`docs/troubleshooting/20260728-응급실-조회-시간필터.md`). 좌표 기반 오퍼레이션이 기관의 진료시간으로 결과를 필터링해 저녁 6시 이후 0건이 되던 문제. 오퍼레이션을 바꾸고 거리 계산을 직접 구현해 해결했고, 공공데이터포털에 오류를 신고해 조회 조건이 수정된 것까지 확인했다.
- CORS 차단 — PR `#40`. 백엔드에 전역 CORS 설정을 넣는 방향으로 발주됐으나, 휴대폰 시연에서 조건이 세 개(각자 PC의 LAN IP·허용 목록·방화벽)로 늘어나 개발 서버 프록시로 방향을 바꿨다. 브라우저에는 동일 출처 요청이 되어 CORS 검사 자체가 발동하지 않는다.

## 4. 다음 주 조정 (3줄 이상)

**목 데이터로 선행 개발하는 방식을 도입한다.** SP2에서 화면 B가 `#24`→`#22`→`#23` 순서로 직렬 대기했던 것이 문제였다. SP3은 계약이 확정된 것을 근거로, 프론트가 계약과 같은 형태의 목 데이터로 화면을 먼저 만들고 실제 연동은 후속 이슈에서 경로만 바꾸도록 나눴다. **프론트가 기다려야 하는 것은 계약이지 구현이 아니다**를 기준으로 삼는다.

**F5의 부하를 콘텐츠 두 건으로 좁힌다.** SP3의 임계 경로가 `F5 정합성 정리 → F5 자료 제작 → T 실제 반영 → F2 연동 확인`이라 머리에 있는 F5가 늦으면 사슬 전체가 밀린다. 정리 작업의 분량이 예상보다 크다(텍스트 20개를 원문과 대조해야 한다). 대신 화상 카테고리는 완성 예시 파일을 만들어 이슈에 첨부했고 F5는 그 형식을 따라 나머지 둘을 만들도록 한다.

**설정값을 임시로 바꿀 때의 규칙을 명시했다.** 트래픽 소진의 원인이 되돌리지 않은 개발용 설정값이었으므로, `application.properties`의 갱신 주기 항목에 "확인하려고 줄였다면 반드시 되돌린다"는 경고와 실제 사고 날짜를 주석으로 남겼다.

## 6. 범위 정리

SP1 회고에서 "3종 경계가 애매해 배제한다"고 했던 **열손상·전기·중독·쇼크**는 SP2 완료 후 정해진 자료 구조상 의식저하 카테고리 안의 개별 섹션으로 들어갈 수 있게 됐다. 계약이 `sections` 구조로 바뀌면서 한 카테고리에 상황별 처치를 여러 개 담을 수 있기 때문이다. **SP3 콘텐츠 자료 제작에서 포함 여부를 F5가 판단**하고 출처와 이용조건이 확인된 것만 넣는다.

## 7. 결정 기록(ADR) 후보

- 응급의료기관 목록과 실시간 가용병상의 캐시 주기를 분리한 결정 - 목록은 6시간·전국 사전 적재, 병상은 3분·조회된 시군구만. 데이터의 변동 속도와 오퍼레이션 단위가 달라 같은 주기를 쓸 수 없었다 (2026-07-30~31 결정)
- CORS를 백엔드 허용 목록이 아니라 프론트 개발 서버 프록시로 해결한 결정 - 휴대폰 시연에서 사람·네트워크마다 갈리는 조건 세 개를 없애기 위한 선택 (2026-07-30 결정, PR `#40`)
- 콘텐츠 API 계약을 `sections` 구조로 바꾼 결정 - 한 카테고리 안에 상황별 처치가 여러 개이고 항목마다 출처·라이선스가 달라 `source`를 섹션 단위로 두어야 했다 (2026-08-02 결정)
- 저확신 판정을 BFF에 두고 `lowConfidence`로 내려보내는 결정 - 기준값이 화면마다 복제되는 것을 막고, 판정 조건이 단일 비교가 아니기 때문(확신도 미만 또는 `unknown`) (2026-08-02 결정)
