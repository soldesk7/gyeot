### 사진 인식 사전 검증 현황

착수 전에 실시한 검증(제품에 사용할 Gemini 엔진이 검증용 사진 20장 전송 시 합격 기준을 통과하는지)에 이번 주 변동이 있었고 재확인 완료.

**무슨 일이 있었나** — BFF 개발 중 **Gemini 모델이 새 계열로 교체된 것이 확인**됐다. 우리가 쓰는 모델 이름(`gemini-flash-latest`)은 최신 모델을 가리키는 별칭이라 우리 코드를 바꾸지 않아도 실제로 호출되는 모델이 바뀔 수 있다. 착수 전 합격 판정은 교체 **전** 모델 기준이었으므로 현재 모델을 더 이상 보증하지 않는 상태가 됐고, 그래서 현재 모델·설정 그대로 20장을 다시 측정했다.

**재측정 결과 (07-23, 검증용 사진 20장)** — 합격 기준 4개 항목 전부 통과

| 항목 | 결과 | 합격 기준 |
|---|---|---|
| 안전 필터 차단 (Gemini가 부상 사진을 거부하는 비율) | 0/20 = 0% | 10% 이하 |
| 분류 일치율 (부상 사진 16장 기준) | 14/16 = 88% | 70% 이상 |
| 대조군 "해당 없음" 응답 (부상 아닌 사진을 응급으로 잘못 판단하지 않음) | 4/4 = 100% | 60% 이상 |
| 응답 시간 | 4.3초 | 10초 이내 |

**카테고리별** — 화상 11장 전부 정확, 의식저하 2장 전부 정확, 출혈 3장 중 1장 정확·2장 "판단 불가", 대조군 4장 전부 "해당 없음".

- 출혈 2장의 "판단 불가"는 **오답이 아니라 안전한 실패 방향**이다 — 확신도가 낮으면 후보를 보여주지 않고 수동 선택으로 넘기는 규칙(기능명세 §0 ③)이 그대로 흡수한다. 출혈이 상대적으로 약한 경향은 이전 측정에서도 일관되게 나타났다.
- 모델 교체로 인한 성능 저하는 없었다. 오히려 이전 측정에서 1건 있던 안전 필터 차단이 0건이 됐고, 응답 시간도 18.7초에서 4.3초로 크게 짧아졌다.

**라벨 검증도 완료** — F5가 진행하기로 했던 20장의 라벨(정답) 육안 확인이 이 재측정 전에 완료 되었고 **20장 전부 수정 사항이 없었다**. 이 20장의 라벨은 원래 사람이 직접 확인한 적이 없어(AI가 고른 사진과 공개 데이터셋의 폴더명을 그대로 쓴 것) "클로드가 화상이라고 인식한 사진을 Gemini도 화상이라고 봤다"는 수준의 근거였는데, 이번 육안 확인으로 그 한계가 해소됐다.

## 2. 목표 달성 여부 (3줄 이상)

- **화면 연결: 달성.** `App.jsx`에 홈(`/`)·사진 인식(`/result`)·가이드(`/guide`, `/guide/:category`)·지도(`/map`)·이용 안내(`/notice`) 5개 경로가 등록됐고, 홈에서 각 화면으로 이동해 다시 돌아올 수 있다. "화면이 다 서 있고 서로 이어져 있다"는 이번 주 목표를 채웠다.
- **119 무차단(N-01)을 구조로 보장했다.** 배너를 라우팅과 페이지 오류 처리 바깥에 두어, 어떤 페이지가 오류로 죽어도 배너는 그대로 남는다. 페이지가 죽으면 "화면을 불러오지 못했어요. 위의 119 배너는 계속 사용할 수 있습니다" 안내로 대체된다 — 빈 화면이 나오지 않는다.
- **BFF는 단독으로 동작한다.** `POST /api/v1/recognitions`에 사진을 올리면 카테고리·확신도·관찰 문장을 돌려준다. 인식이 실패하거나 안전 필터에 걸려도 예외를 밖으로 던지지 않고 `unknown`으로 흡수해 화면이 멈추지 않게 했다.
- **다만 화면과 BFF는 아직 연결되지 않았다.** 어느 페이지도 API 래퍼를 호출하지 않으며, 가이드 화면은 임시 데이터로 그린다. 이건 계획대로 SP2 범위다.
- **공용 패턴도 이번 주에 확정했다.** 홈 화면이 원본이고, 새 화면은 이걸 복사해서 시작한다. 세 가지뿐이다.
  - **`.page`** — 화면 전체를 감싸는 틀. 최대 폭을 480px로 잡아 휴대폰 화면을 기준으로 삼았고, 안의 요소들은 세로로 12px 간격을 두고 쌓인다. PC에서는 가운데 좁은 기둥처럼 보인다.
  - **`.action`** — 큰 버튼. 위아래 20px 여백에 20px 굵은 글씨, 2px 테두리를 준다. 경황이 없는 상황에서 손가락으로 정확히 겨누지 않아도 눌리도록 크게 잡은 것이다(N-04). 119처럼 위험을 알려야 하는 버튼은 `.action--danger`를 함께 붙여 빨간 배경으로 만든다.
  - **`.card`** — 안내문이나 상태를 담는 고대비 상자. 2px 테두리에 안쪽 여백 16px.
  - 배너는 이 셋과 별개로 `.banner119`가 화면 맨 위에 붙어 스크롤해도 따라온다.
  - API 호출도 마찬가지로 `api/client.js`의 공통 래퍼를 거치게 하고 본보기(`guides.js`)를 만들어 뒀다. 새 API 래퍼는 이 파일을 복사해서 만든다.

## 3. 막힌 것 (3줄 이상)

- **Gemini 인식이 전면 실패했다(해결).** 모델이 새 계열로 바뀌면서 기존 설정값을 거부해 모든 요청이 400 오류로 돌아왔다. 우리 코드는 그대로였는데 외부 사정으로 깨진 경우라 원인 파악이 늦어졌고, 라이브러리가 원본 오류 메시지를 뭉개서 보여준 것도 진단을 더디게 했다. 설정값 하나를 바꿔 해결.
- **탑재할 수 있는 콘텐츠가 확보되지 않았다(미해결).** 가이드 화면에 무언가 들어가 있는 건 화상 1건뿐인데, 그것도 이미지·영상이 제대로 뜨는지 확인하려고 넣은 임시 데이터이지 실제 공식 콘텐츠가 아니다. **3종 모두 실제 콘텐츠는 아직 0건이다.** 콘텐츠 수집(#7)이 닫히지 않아 채울 재료가 없다. F2는 임시 데이터로 SP1 완료 기준을 채웠으므로 이번 주에 작업이 멈추지는 않았지만, 실제 콘텐츠로 잇는 작업은 재료가 들어와야 시작된다.
- **CSS가 다른 화면까지 새어 나갔다(해결).** 가이드 화면용 CSS가 전역으로 적용돼, 그 CSS를 가져오지 않은 화면에서도 이미지가 안 뜨는 문제가 있었다(#13). 태그 전체가 아니라 클래스에만 적용되도록 바꿔 해결(PR #14).

## 4. 다음 주 조정 (3줄 이상)

- **PR을 마감일 당일에 올리지 않는다.** 이번 주 PR 제출 시각을 보면 차이가 뚜렷하다 — 하루 전에 올라온 것들은 여유 있게 검토·머지됐지만, 마감일(07-24) 오후에 올라온 PR은 검토 시간이 남지 않아 그대로 다음 주로 넘어갔다. SP2는 5일이므로 **목요일까지 PR을 올리는 것**을 기준으로 잡고, 늦어질 것 같으면 미리 공유한다.
- **SP2 목표를 줄이고 담당을 재배치했다(팀장 결정, 07-27).** 원래 SP2 목표는 업로드부터 가이드까지 전부 실데이터로 잇는 것이었으나, 가이드에 넣을 콘텐츠가 아직 없어 마지막 고리를 채울 수 없다. 그래서 **가이드 실데이터 연결을 SP3로 미루고, SP2 목표는 "업로드→인식→확인까지 실데이터로 잇는다"로 줄인다.** 가이드 화면은 SP2까지 임시 데이터로 이어 붙인다.
- **기다리는 사람이 생기지 않도록 순서를 맞췄다.** 콘텐츠를 기다리게 된 F2는 화면 B(사진 업로드)로 옮기고, 응급실 API가 없어 지도를 못 잇던 F1을 위해 **응급실 프록시 API를 SP3에서 SP2로 당긴다**(병상 캐싱은 SP3 그대로). 소비자가 SP3로 간 콘텐츠 API도 SP3로 함께 옮긴다. 이 조정으로 SP3에 T 작업이 몰리므로, **SP2가 일찍 끝나면 병상 캐싱을 앞당겨 SP3 부하를 던다.** 업로드 화면에 띄울 처리 고지 팝업은 고지 문구를 쓴 F4가 그대로 맡아, F2가 화면을 만들기 전에 목업으로 먼저 머지한다.
- **외부 API가 예고 없이 바뀔 수 있다는 걸 이번 주에 겪었다.** 우리 코드는 그대로인데 모델이 교체되면서 인식이 전부 실패했고, 원인을 찾아 고치는 데 한 시간 남짓 들었다. 모델을 특정 버전으로 고정하는 방법도 있지만, 이번 프로젝트는 오래 운영하지 않고 인식이 통째로 실패하면 바로 알아챌 수 있는 구조라 **고정하지 않기로 한다.** 대신 인식이 갑자기 전부 실패하면 우리 코드보다 **모델 교체를 먼저 의심한다.**
