## 요약 (먼저 읽을 것)

SP3까지가 기능을 만드는 주였다면 SP4는 **만든 것을 요구사항에 맞추고 범위를 닫는 주**였다. 새 기능은 하나도 늘리지 않았고, 여섯 항목을 정해 그것만 했다.

세 가지가 이번 주의 성격을 결정했다.

- 월요일 범위동결 게이트에서 **B안(신규 개발 동결)을 택했다.** Could 등급 셋과 F-09E는 이월로 확정했고 다시 꺼내지 않는다.
- **119 배너가 클릭되지 않는 상태였던 것을 주중에 발견했다.** 사진 처리 고지가 배너 위를 덮고 있었고, 이는 불변 원칙 3(119 무차단) 위반이다. 세 번의 시연 동안 아무도 보지 못했다.
- **확인 방식을 성공 경로 시연에서 명세 대조로 바꿨다.** 명세 ID별 38항목 체크리스트를 만들고 담당을 교차로 배정해 1차 수행을 했다. 위 발견과 SP3의 N-05 미충족이 같은 원인에서 나왔기 때문이다.

### 계획에 없던 것 — 주중에 발견해 처리

**사진 처리 약관 팝업의 119 배너 클릭 차단** (`#100`·PR `#102`). 고지 영역이 배너 위에 겹쳐 그려져 탭이 배너에 닿지 않았다. 처리 고지가 보이는 것에 집중하여 배너가 클릭되지 않는 상태임을 눈치채지 못했고 실제로 눌러보기 전에는 드러나지 않는 종류의 문제였다. 불변 원칙 3과 N-01은 "AI·네트워크 상태와 무관하게 119가 동작할 것"을 요구하는데, 이 경우는 우리 화면이 스스로 막고 있었다. 배너 높이가 기기마다 달라 처리 고지 화면을 픽셀값을 고정하는 방법으로는 해결할 수 없었고 레이아웃 구조를 기준으로 배치를 다시 잡아 해결했다.

**실기기에서의 위치정보 확인 불가** (`#103`·PR `#104`). 브라우저는 HTTPS나 `localhost`가 아니면 위치정보를 차단한다. 개발 서버가 HTTP라 실기기를 서버 주소로 열면 권한 팝업 자체가 뜨지 않았고, 주소 검색 폴백만 확인되는 상태였다. 개발 서버를 HTTPS로 바꿔 해결했다.

### 시연을 QA 체크리스트 수행으로 대체

계획서의 SP4 완료 기준은 "Must 전부를 합쳐서 한 번에 시연"이다. 이번 주에는 시연 대신 체크리스트 38항목 수행으로 그 자리를 채웠다.

시연은 담당자가 아는 경로를 밟아 잘 되는 것을 보이는 자리다. 이번 주에 확인해야 했던 것은 그게 아니라 **명세를 실제로 충족하는가**였고, 그건 항목을 하나씩 대조해야 알 수 있다. 지난 세 번의 시연이 N-05 미충족과 119 배너 클릭 차단을 모두 놓친 것도 형태의 문제였다. 시연 한 번이 커버하는 경로보다 체크리스트 38항목이 넓고 같은 시간에 더 많은 것을 확인한다.

### 범위 결정

월요일 게이트에서 **B안(신규 개발 동결)** 을 택했다. 판단 재료는 Must 4건이 전부 동작하는 상태였고 열린 이슈가 콘텐츠와 QA뿐이었다는 점, 그리고 요구사항 미충족 항목(전 가이드 화면 비진단 고지)과 출처 없는 문구(119 신고 안내)가 남아 있었다는 점이다. 새 기능을 얹는 것보다 이 둘을 해결하는 것이 급선무였다.

## 2. 목표 달성 여부 (3줄 이상)

**기능 완결** — B안 여섯 항목이 모두 완수되었다. 요구사항 미충족이던 전 가이드 화면 비진단 고지와 출처가 확인되지 않던 119 안내 문구가 해소됐다. Must 4건이 전부 동작하는 것은 시연이 아니라 체크리스트 38항목 대조로 확인했다.

**범위동결** — 이번 주에 새 기능이 들어오지 않았다. Could 등급 셋과 F-09E는 이월로 확정했다. 게이트를 월요일에 둔 것은 "시작할지"를 정하는 판정이 금요일에 오면 시작할 주가 남지 않기 때문이었다.

**QA** — 체크리스트 38항목을 작성하고 1차 수행을 마쳤다. SP4 크롬 38항목 통과, 삼성 인터넷은 32항목 통과에 6항목이 브라우저와 무관해 해당 없음이다. 실패로 기록된 항목은 없다. 이것이 무엇을 뜻하는지는 3절에 적었다. 수행이 주 후반으로 밀린 원인도 같은 절에 있다.

## 3. 막힌 것 (3줄 이상)

### 성공 경로만 밟는 확인은 요구사항 위반을 잡지 못한다

이번 주에 발견한 119 배너 클릭 차단은 SP3에서 놓친 N-05 미충족과 원인이 같다. 지금까지 시연은 담당자가 아는 경로로 잘 되는 흐름만 밟았고 명세와 대조하지 않았다. 화면에 보이기만 하면 통과로 넘어갔기 때문에 "보이지만 눌리지 않는" 상태를 아무도 확인하지 않았다. 세 번의 시연이 같은 방식이었고 세 번 다 놓쳤다.

### 콘텐츠 자료의 판정과 표기가 섞여 있었다

영상 4건 각각에 대해 운영기관의 저작권 정책을 확인한 근거가 남아 있었고, 두 번의 제출본에서 그 판정은 같았다. 어긋난 것은 표기였다 — 자료명의 낫표, 기관명과 자료명 사이 공백, 이용조건 필드에 원자료 출처가 섞여 들어간 것이 제출본마다 달랐고, 한 번 고친 뒤에도 다른 자리에서 같은 종류의 오류가 나왔다. 열다섯 자리를 사람이 눈으로 맞추는 방식이었다.

### 체크리스트를 만들고 즉시 수행하여 수정 기간이 짧았다.

초안이 목요일에 나와 검토를 거쳐 금요일에 확정됐고 수행도 금요일에 실행했다. 이번에는 실패가 없어 넘어갔지만 여러 건 나왔다면 수정할 시간이 없었다.

수행 담당을 화면 단위로 나눈 것도 손봐야 했다. 서버와 빌드 산출물을 보는 항목(N-03)은 화면 담당 누구에게도 가지 않았고 저확신 전환처럼 두 화면에 걸친 항목은 양쪽 다 "내 화면이 아닌것 같다"로 넘길 수 있었다. 배정을 명세 ID로 변경하여 메웠다.

38항목이 전부 통과했지만 이것을 품질이 좋다는 뜻으로 읽으면 안 된다. 지금 항목이 잡을 수 있는 범위 안에서는 문제가 없다는 뜻이고, 그 범위가 얼마나 넓은지는 이 결과로 알 수 없다. 이번 주에 드러난 문제 둘도 체크리스트가 아니라 화면을 직접 만지다 나왔다.

## 4. 다음 주 할 일 (SP5: 08-17 월 ~ 08-21 금)

목표: **안정화 — 실패해도 죽지 않는 사이트** 신규 기능 개발 동결

- **장애 폴백 시나리오 확장.** 성공 기준이 "실패 시나리오 100% 통과"인데 지금 N-08 항목 넷은 전부 단일 실패다. 두 가지가 겹쳐 실패하는 경우와 응답이 오다 끊기는 경우를 다룬다
- 그 과정에서 나온 문제 처리
- 코드를 고친 경우 그 수정이 닿은 범위만 체크리스트로 다시 확인한다. 회차를 나눠 기록하고 1차 결과는 지우지 않는다
- 발표 자료 준비 — 두 프로젝트에서 각자가 담당했던 역할에 대하여 개별 준비 및 팀명 확정

**밀린 트러블슈팅 문서 작성.** 지금 남은 문서는 세 건인데, 이번 주만 해도 119 배너 클릭 차단(`#100`)은 `z-index`와 `pointer-events`를 거쳐 레이아웃 구조로 푼 과정이 있었고 실기기 위치정보도 확인 환경을 만드는 데 시간이 들었다. 시간이 더 지나면 진단 과정이 기억에서 뭉개져 "어려웠지만 해결했다"밖에 남지 않는다. 해결한 사람이 작성한다.

## 6. 팀원 소감

각자 이번 주에 배운 것을 본인 서술로 남긴다.

**F4 — 레이아웃 구조로 푼 CSS 문제**

이번 주에는 `#88`·`#91`·`#100` 작업을 진행했고, 다른 팀원이 만든 응급실 지도 기능도 직접 테스트해 정상 동작을 확인했다.

`#91`에서는 다른 사람이 작성한 코드의 흐름을 파악하는 데 시간이 걸렸다. `#100`은 기존 사진 처리 고지가 119 배너의 클릭을 막는 문제였는데, 원인을 찾고 수정하는 과정이 조금 어려웠다. 특히 **119 배너의 크기가 고정된 값이 아니라 기기마다 달라질 수 있어** 해결하기 어렵다고 느꼈다.

처음에는 `z-index`나 `pointer-events`를 쓰는 방법을 시도했지만, 최종적으로는 `.app-content`를 위치 기준으로 삼아 `position: relative`와 `position: absolute`의 관계를 활용해 사진 처리 고지를 그 영역 안에 배치하는 방식으로 수정했다. **특정 픽셀 값을 지정하는 것보다 화면의 레이아웃 구조를 기준으로 CSS 문제를 해결하는 방법**을 배웠다.

처음 생각했던 방법으로 문제가 해결되지 않았을 때, 바로 다른 코드를 수정하기보다 현재 구조를 다시 확인하면서 해결 방법을 찾아가는 과정이 필요하다는 것을 느꼈다.

## 7. 결정 기록(ADR) 후보

SP6 문서 주간에 소급 작성한다.

- 범위동결 게이트를 금요일이 아니라 스프린트 시작 월요일에 둔 이유
- 확인되지 않은 이용조건의 자료는 출처를 표기하더라도 내린다는 기준
- 개발 서버를 HTTPS로 운영하는 이유 (위치정보가 보안 컨텍스트를 요구한다)
