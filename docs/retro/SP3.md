## 요약 (먼저 읽을 것)

SP2에서 화면과 BFF를 연결했다면 SP3는 그 위에 **공식 기관의 실제 자료**를 얹고 **인식이 실패했을 때의 예외처리를**을 만든 주였다.

세 가지가 이번 주의 성격을 결정했다.

- 저확신·인식 실패를 화면이 아니라 **BFF가 판정해서 한 값(`lowConfidence`)으로 내려보내기로** 계약을 정리했다. 프론트가 기준값을 갖지 않는다.
- 콘텐츠 자료가 **기능 개발 완료 된 후에** 반영됐다. 이용조건(공공누리 제4유형 변경금지) 확인에 시간이 걸렸다.
- **오류 계약을 두 번 뒤집었다.** 요청 한도를 별도 오류로 낼지 흡수할지가 그 대상이었고, 결론은 "429만 오류, 나머지는 200으로 흡수"다.

## 2. 목표 달성 여부 (3줄 이상)

**인식 예외 경로는 목표대로 끝났다.** 저확신·안전 필터 거부·타임아웃·요청 제한이 어떤 경로로 오든 화면이 수동 선택으로 이어진다. 빈 화면이 나오는 경로가 없다는 것을 실제 응답과 서버 종료 두 방식으로 확인했다.

**콘텐츠는 목표를 절반만 달성했다.** API와 화면이 완성된 시점에 실제 자료는 화상 한 종만 들어갔다. 출혈외상·의식저하는 이용조건 확인이 끝나지 않아 자리표시자로 남았다가 주 후반에 반영됐다.

**계약 정리가 예상보다 큰 비중을 차지했다.** 코드를 작성하는 시간보다 "무엇을 오류로 볼 것인가"를 정하고 문서를 수정하는 데 시간이 더 들었다. 다만 그 덕분에 화면이 직접 오류 코드별로 분기하지 않아도 되는 구조가 됐다.

## 3. 막힌 것 (3줄 이상)

### 콘텐츠 자료 — 이용조건이 병목이었다

수집한 자료 중 상당수가 공공누리 **제4유형(출처표시·비상업적·변경금지)**이었다. 변경금지는 문장을 다듬거나 여러 출처를 합치는 것도 허용하지 않는데, 처음 제출받은 자료는 원문을 단계별로 다시 쓴 상태였다. 질병관리청 원문과 한 줄씩 대조해 확인했다.

세 번의 제출을 거쳐 화상 한 종이 통과했다. **원문을 그대로 옮긴 예시가 하나 생기고 나서 기준 전달이 훨씬 빨라졌다** — 말로 설명하던 것보다 통과한 파일을 보여주는 쪽이 효과적이었다.

**아직 열린 항목**: 가이드에 실린 영상 4건의 채널 퍼가기 허용 여부가 확인되지 않았다. 확인 전까지 화면 노출 여부를 판정해야 한다.

**왕복이 길어진 구조적 이유**도 함께 드러났다. 자료 제작은 산출물이 코드가 아니라 **PR 리뷰 경로를 타지 않는다.** 그래서 진행 중에는 아무도 상태를 볼 수 없고 완성본을 받아본 뒤에야 문제를 발견하게 된다. 리뷰 담당도 같은 어려움을 지적했다 — 작업 방식과 세부 진행도를 파악할 방법이 없었다는 것이다.

### 담당 조정

F3가 맡던 인식 예외 경로 작업을 주 후반에 T가 이어받아 마무리했다. 작업 중이던 PR을 그대로 이어받아 커밋을 얹는 방식으로 처리해 이력이 끊기지 않도록 작업했다.

### 응답 형식 문제를 우연히 발견했다

PR 검토 중 첨부된 스크린샷이 XML이었다. 브라우저 주소창으로 API를 열면 XML이 나가고 있었는데, 프론트는 `fetch` 기본 헤더 덕분에 JSON을 받고 있어 화면상으로는 드러나지 않았다. **계약이 지켜진 게 아니라 브라우저에서 알맞은 헤더를 보내고 있던 상태였다.**

공공데이터 XML을 파싱하려고 넣은 의존성만으로 XML 응답 변환기가 자동 등록된 것이 원인이었다.

### 시연 리허설 — 사용할 입력값을 정해두지 않아 두 번 지체했다

**사진 크기 오류가 재현되지 않았다.** 업로드 상한을 낮춰 오류 화면을 보여주려 했는데 몇몇 사진은 그대로 인식됐다. 검증용 사진 20장 중 10장이 그 상한보다 작아 통과한다.

**주소 검색에 시간이 걸렸다.** 응급실 지도의 주소 검색은 도로명 주소를 정확히 입력해야 결과가 나온다. 사용할 주소를 정해두지 않아 현장에서 찾느라 몇 초를 소비했다.

원인이 같다 — **시연에서 사용할 입력값을 미리 정해두지 않았다.** "적당한 사진", "아무 주소"로 두면 현장에서 고르게 되고 그 값이 조건을 만족하는지는 그때 확인해야 된다.

## 4. 다음 주 조정

- **QA 체크리스트에 시연 시 사용할 자료를 정해둔다.** 파일 경로·검색어·좌표까지. "준비한다"가 아니라 무엇을 준비하는지가 값으로 있어야 한다. 리허설에서 그 값으로 한 번 통과시킨다.
- **시연 중 서버 설정을 바꾸지 않는다.** 재기동이 필요하고 그 과정에서 캐시가 날아간다. 준비물로 해결할 수 있는 것은 준비물로 해결한다.
- **이용조건 확인을 자료 수집과 같은 단계에서 끝낸다.** 이번에는 자료를 받은 뒤에 확인하다 세 번을 왕복했다. 출처와 이용조건이 채워지지 않은 자료는 받지 않는 편이 서로 빠르다.
- **코드가 아닌 산출물도 중간에 보이게 한다.** 자료·문서 작업은 PR 리뷰를 거치지 않아 완성본을 받을 때까지 상태를 알 수 없다. 한 카테고리를 먼저 제출받아 기준을 맞춘 뒤 나머지를 진행하는 방식이 효과가 있을 것으로 보인다 — 직접 검수하여 통과한 예시 하나가 말로 하는 설명보다 빨랐다.
- **계약을 바꿀 때 영향받는 이슈를 함께 확인한다.** 오류 계약을 정리하면서 이미 발주된 이슈의 완료 기준이 현실과 어긋나는 일이 몇 번 있었다.

**F-13 119신고 앱·다매체 신고 안내 페이지**

지금 119로 가는 경로는 배너의 전화 걸기 하나뿐이다. **소리를 낼 수 없는 상황이거나 청각·언어 장애가 있으면 대체 경로가 없다.**

공식 채널이 넷 있다는 것을 확인했다.

| 경로 | 준비 | 특징 |
|---|---|---|
| 문자(SMS/MMS) | 불필요 | 사진·동영상 첨부 가능 |
| 영상통화 | 불필요 | 화면으로 현장 전달 |
| 119신고 앱 | 설치 필요 | 위치가 함께 전달됨 |
| 웹(119.go.kr) | 본인인증·주소 입력 필요 | 안내문상 대상이 "말하기 불편한 장애인, 한국어가 서툰 외국인"으로 한정 |

- **규모**: 정적 화면 1개. 새로 붙는 외부 의존이 없어 안정화 부담이 거의 없다
- **준비 상태**: 채널·이용 방법·출처를 이미 확인했다. 남은 건 화면 구현과 진입점 결정
- **주의**: 웹 신고는 본인인증이 필요해 "지금 바로"가 아니다. 앱도 설치가 필요하다. 화면에서 **지금 쓸 수 있는 것과 미리 준비할 것을 나눠 배치**해야 한다

**F-16 AED 위치 표시**

의식저하 가이드가 심폐소생술과 자동심장충격기 사용법을 안내하는데 **"어디 있는지"는 알려주지 못한다.** 콘텐츠와 지도가 끊겨 있는 구멍이다.

- **규모**: 백엔드에 공공데이터 오퍼레이션 1개 추가(캐싱·테스트 포함) + 지도 마커 구분·범례
- **부담**: 다음 주가 안정화 주간인데 **새 외부 의존이 하나 늘면 실패 시나리오도 하나 늘어난다**
- 만들 가치가 없어서가 아니라 시점이 맞지 않는 쪽이다. 하지 않기로 하면 차후 과제로 이월하는 게 맞다

**F-15 시연 데모 모드**

샘플 사진으로 정해진 시나리오를 돌리는 모드.

- **목적**: 시연 안정성. 이번 리허설에서 겪은 문제(입력값 미고정)를 구조적으로 없앤다
- **대안이 이미 있다**: 4절의 조정 항목 — 시연에 사용할 입력값을 미리 정해두고 리허설에서 통과시키는 것 — 이 같은 문제를 더 싸게 해결한다
- **부작용**: SP3에서 목 응답 체계를 만들었다가 실연동이 끝나 지웠다. 다시 넣으면 시연용 경로가 제품 코드에 남아 실제 동작과 갈라진다

**F-09E 분류 카테고리 확대(3종→6종)**

경련·기도폐쇄·골절을 인식 범주에 추가.

- **부담이 가장 크다**: 범주를 늘리면 검증용 사진으로 합격선을 다시 통과해야 하고, **콘텐츠도 3종을 더 만들어야 한다**
- 지금 3종의 이용조건 정리도 끝나지 않았다
- 기능 명세에 "컷 1순위"로 표기돼 있다

## 7. 범위 정리

- 요청 대기열은 만들지 않기로 했다. 대기시키는 동안 사용자가 아무것도 못 하므로 즉시 수동 선택으로 보내는 편이 낫다.

- 목록 응답의 `summary`를 제외했다. 공식 출처에 없는 문장을 새로 써야 하기 때문이다. (공공누리 제4유형에 위배)

## 8. 팀원 소감

각자 이번 주에 배운 것을 본인 서술로 남긴다.

**F1 — 지도와 오류 처리**

카카오맵 Geocoder로 주소를 좌표로 바꾸고, 마커·오버레이를 배열과 ref로 추적했다가 재검색 시 지우고 다시 그리는 패턴을 구현하며 익혔다. 오류 처리에서는 실패 응답을 항상 같은 형태(`ApiError`)로 통일해 던지는 것의 중요성과, `??`와 `||`의 차이(빈 문자열을 falsy로 볼지)가 실제 화면 버그로 이어질 수 있다는 것을 배웠다. `setTimeout`과 `setInterval`을 조합해 "정확한 시점까지 한 번 기다렸다가 이후 반복 갱신하는" 2단계 타이머를 설계하면서, 타이머가 화면 상태만 바꾸고 API 호출과는 분리돼야 한다는 원칙도 코드로 확인했다.

**F2 — 유튜브 영상이 재생되지 않던 문제**

- 증상: 화상 가이드의 영상 구획이 검은 화면만 뜨고 재생되지 않았다
- 원인: `<video src>`에 유튜브 시청 페이지 주소(`watch?v=…`)를 그대로 넣었다. `<video>`는 mp4 같은 파일만 재생할 수 있고 HTML 페이지는 재생하지 못한다
- 해결: 렌더링 시점에 URL이 유튜브면 embed 주소로 바꿔 `<iframe>`으로, 아니면 그대로 `<video>`로 그리도록 분기를 추가했다. 콘텐츠 JSON은 건드리지 않았다

**F3 — 협업과 AI 활용**

맡은 기능을 완성하는 것만이 아니라 다른 팀원이 다음 작업을 진행할 수 있도록 일정에 맞춰 개발하는 것이 중요하다는 것을 느꼈다. 모르는 부분을 완벽히 이해한 뒤 진행하려다 오히려 문제의 범위를 정리하지 못하고 시간을 쓴 경우가 있었고, 해당 코드를 작성한 팀원에게 질문하거나 도구를 활용해 빠르게 방향을 찾는 편이 효율적이라는 것을 배웠다.

AI가 제안한 코드를 그대로 쓰지 않고 동작 원리를 확인해 상황에 맞게 고치려 했으나, 완전히 이해하지 못한 상태에서 수정하다 보니 다른 기능에 응용하거나 동작을 설명하는 데 어려움이 있었다. **AI를 쓰는 것 자체보다 생성된 코드의 구조와 원리를 이해하고 필요한 부분을 스스로 판단하는 능력이 중요하다**는 것을 느꼈다. 앞으로는 바로 코드를 쓰기보다 글이나 의사코드로 흐름을 정리하고 설계한 뒤 개발하는 습관을 들이고 싶다.

**F4 — 데이터 흐름과 실기기 점검**

카테고리 선택 화면과 목 데이터 작업, 모바일 점검을 진행했다. 개발자 도구는 Elements와 Console 위주로 썼었는데 이번에 **Network 탭에서 API 요청과 응답을 확인하는 방법**을 익혔다. 카테고리 버튼이 직접 작성되는 것이 아니라 백엔드나 JSON에서 받은 데이터로 생성될 수 있다는 점도 새로 알게 됐다.

리액트로 만든 프로젝트를 실제 모바일 기기에서 테스트한 것은 처음이었고, 개발 서버를 모바일과 연결해 동작을 확인하는 방법을 경험할 수 있었다. 새로 접한 용어와 코드, 데이터 흐름을 바로 연결해 이해하는 데 아직 시간이 걸려 실제 코드와 함께 반복적으로 확인하며 익숙해지려 한다.

**P — 리뷰 관점**

첫 팀 프로젝트에 비해 팀원들의 참여도와 협조율이 높아져 수월하게 진행할 수 있었다. 다만 **코드가 아닌 산출물(자료·문서)은 리뷰 경로를 타지 않아** 작업 방식과 세부 진행도를 파악하기 어려웠다 — 3절·4절에 조정 항목으로 옮겼다.

## 9. 결정 기록(ADR) 후보

- 인식 실패를 오류로 내리지 않고 200 응답의 한 값으로 흡수한 결정 — 화면이 실패 원인을 알 필요가 없게 만든 구조
- 응답 형식을 JSON으로 고정한 결정 — 파싱용 의존성이 응답 형식에 영향을 준 사례
- 기준 시각을 병상 수집 시각으로 옮긴 결정 — 여러 시군구가 섞일 때 가장 이른 시각을 쓰는 이유
