# 응급실 조회 결과가 시간대에 따라 변함을 확인 — getEgytLcinfoInqire의 진료시간 필터

> - 발생일: 2026-07-27 저녁 ~ 2026-07-28 오후 (SP2)
> - 관련 기능: F-05 (응급실 지도, BFF → 공공데이터포털)
> - 작성자: 송승준(T)
> - 소요: 이틀 (1일차 저녁 원인 규명·DTO 전환, 2일차 오후 구조 수정·검증)

## 증상

`GET /api/v1/emergency-rooms?lat=37.4881326&lng=127.0851566`(강남 삼성서울병원 앞 좌표)로 조회했을 때, 브라우저에서 공공데이터를 직접 호출한 결과와 우리 앱의 응답이 전혀 달랐다.

| | 첫 결과 | 건수 |
|---|---|---|
| 브라우저 직접 호출(오후 3시경) | 삼성서울병원 0.14km | totalCount 60 |
| 우리 앱(오후 5시 56분) | 서울대학교병원 12.7km | 4건 |

같은 좌표인데 가장 가까운 병원들이 통째로 빠졌고, `numOfRows=20`을 요청했는데도 4건만 돌아왔다.

## 원인

`getEgytLcinfoInqire`(응급의료기관 위치정보 조회)가 **기관의 진료시간(`startTime`~`endTime`) 기준으로 결과를 필터링**하고 있었다. 즉 조회 시각에 이미 마감한 기관은 목록에서 제외되는 것이 확인되었다.

시간대별로 재현한 결과:

| 조회 시각 | totalCount | 비고 |
|---|---|---|
| 15:15경 | 59~60 | `endTime`이 1530·1700·1730 등 다양 |
| 17:56 (동일 조건 재시도 3회) | 4 | 반환된 4곳의 `endTime`이 **전부 1800** |
| 18:05 | **0** | 전멸 |

응급실이 가장 필요한 밤·새벽에 지도가 텅 비는 구조라, 이 오퍼레이션으로는 F-05를 만들 수 없었다. 활용가이드(NIA-IFT-OpenAPI활용가이드-01, V4)의 해당 오퍼레이션 설명에는 이 필터 조건이 명시돼 있지 않다.

## 진단 과정

**1단계 — 가설 ① 우리 앱이 URL을 잘못 조립하고 있다**

같은 좌표인데 결과가 다르니 요청이 잘못 나가고 있다고 의심했다. `logging.level.org.springframework.web.client=DEBUG`를 켰으나 `RestClient`는 요청 URL을 로그로 남기지 않아 확인할 수 없었다. 대신 우리 앱과 **동일한 조건**(XML 형식, `numOfRows=20`)으로 직접 호출해 비교했더니 12.7km부터 4건이라는 **똑같은 결과**가 나왔다. 우리 코드는 정상이고 API가 그렇게 응답한다는 것이 확정됐다.

**2단계 — 응답 데이터에서 단서 발견**

결과가 매번 동일한 4건이라는 점(무작위가 아닌 결정론적 동작), 그리고 거리 값 자체는 실제와 맞다는 점(강남<->서울대병원 12.7km)에서 좌표는 정상 전달되고 있다고 판단했다. 그렇다면 "왜 가까운 병원만 빠지는가"가 남는데 응답의 `endTime`이 4곳 모두 `1800`이고 당시 시각이 17:56이라는 것이 눈에 띄었다. 오후 3시대 API 테스트 조회에서는 `endTime`이 1530·1700·1730으로 다양했던 것과 대비됐다.

**3단계 — 시간대별 재현으로 확정**

18시가 지난 뒤 동일 좌표로 재조회하니 `totalCount`가 **0**이 됐다. 진료시간 필터 가설이 확정됐다.

**4단계 — 대체 오퍼레이션 검증**

활용가이드의 오퍼레이션 9종을 재검토해 `getEgytListInfoInqire`(응급의료기관 목록정보 조회)를 후보로 골랐다. 같은 함정을 다시 밟지 않도록 코드를 고치기 전에 응답부터 확인했다.

- 18시 이후인데도 `totalCount` **534**(전국 응급의료기관) 정상 반환 → 시간 필터 없음
- `wgs84Lat`/`wgs84Lon` 좌표 제공, `dutyEmclsName`(기관 등급)·`dutyTel3`(응급실 직통 전화) 추가 제공
- 단, `distance`를 주지 않고 정렬도 기관명 오름차순 → 거리 계산·정렬은 우리 몫

## 해결

`getEgytListInfoInqire`로 전환하고, API가 해주지 않는 부분을 서비스 계층에서 처리하도록 수정했다.

1. **오퍼레이션 전환** — `EmergencyRoomClient`가 좌표 없이 전국 목록(`numOfRows=1000`)을 받아온다.
2. **거리 계산** — `EmergencyRoomService`에 하버사인 공식을 추가해 사용자 좌표로부터의 직선거리를 미터로 계산하고 가까운 순으로 정렬해 상위 20곳만 반환한다.
3. **좌표 결측 처리** — 534건 중 좌표가 비어 있는 기관이 섞여 있어 `double`로는 파싱이 통째로 실패하는 경우가 생겼다(`Cannot map null into type double`). DTO 필드를 `Double`(래퍼 클래스)로 변경하고 서비스에서 결측 기관을 제외하도록 결정했다. `0.0`으로 대체하면 위경도 (0,0) = 아프리카 앞바다로 계산돼 정렬이 망가지므로 기본값 대체는 쓰지 않았다.
4. **타임아웃 상향** — 전국 목록(534건·230KB) 실측 응답 시간이 약 7초여서 기존 `readTimeout` 5초를 초과했다. 간헐적 타임아웃의 원인이기도 해서 10초로 상향했다. (활용가이드에는 9개 오퍼레이션 모두 "평균 응답 시간 500ms"로 동일하게 기재돼 있어서 오퍼레이션별 실측값으로 보기 어렵다)

### 거리 계산 검증

검증 결과, 계산한 거리가 `Lcinfo`가 제공하던 값과 일치했다.

| 기관 | Lcinfo 제공 값 | 하버사인 계산 |
|---|---|---|
| 삼성서울병원 | 0.14 km | 141 m |
| 강남세브란스 | 3.47 km | 3466 m |
| 서울아산병원 | 4.73 km | 4734 m |

### 대안 검토 — 주소 기반 필터링
`ListInfo`는 주소(`Q0` 시도·`Q1` 시군구)로 범위를 좁힐 수 있어 응답 크기와 시간을 줄이도록 할까 고민했었으나 채택하지 않았다.
행정구역으로 필터링하면 경계 지역에서 요청 시 더 가까운 병원이 누락될 우려 때문이다.(성남 판교에서 조회할 때 바로 옆 서울 서초구 병원이 누락되는 경우) 응급 상황에서 행정구역 때문에 가까운 응급실이 보이지 않는 것은 위험하므로 전국 목록을 받아 거리순으로 정렬하는 방식을 택했다.
실제로 강남 좌표로 조회하면 성남시의료원·성남중앙병원이 서울 기관들과 섞여 거리순으로 출력되는 것을 확인했다.
후속 작업으로 응급실 목록 캐싱을 구현한다면 응답 시간 문제를 해결할 수 있다고 보았으므로 주소 필터로 얻는 조회 시간 단축의 이점이 크지 않다는 것이 최종 판단이었다.

## 후속 — 데이터 제공기관 문의 및 수정 확인

원인이 확정된 뒤 공공데이터포털(Data.go.kr)의 오류신고로 접수했다. 해당 데이터의 담당기관은 국립중앙의료원이며, 처리 결과는 포털 운영기관(한국지능정보사회진흥원)을 통해 회신됐다.

> **문의 요지**
> 1. 조회 시각에 따라 `totalCount`가 59~60 → 4 → 0으로 달라지는 동작이 의도된 사양인지 확인 요청
> 2. 의도된 사양이라면 활용가이드에 시간 필터 조건이 명시돼 있지 않으므로 문서 보완 가능한지 문의
> 3. 응급의료기관은 24시간 운영이 전제되는 정보인데, 좌표 기반으로 시간과 무관하게 조회할 방법이 있는지 안내 요청

> **오류처리내용(2026-07-28 회신)**
> "확인 결과, 외상센터는 24시간 운영되는 기관으로 확인되어, 운영시간 외 기관만 표출되도록 적용되어 있던 조회 조건을 수정하였습니다."

답변에 언급된 대상(외상센터)이 문의 대상(응급의료기관)과 달라 실제 반영 여부를 실측으로 확인했다. 
**2026-07-28 16:00 기준**:

- `endTime` **1530**인 기관이 결과에 포함 → 현재 시각 기준 이미 마감한 기관이 나옴
- `totalCount` **87** (같은 좌표 기준 15시대 59~60보다 증가 — 필터가 남아 있다면 오히려 줄어야 함)
- `endTime` **2359·2400**(24시간 운영) 값 등장 — 이전 관찰에는 없던 값

세 가지 모두 시간 필터가 해제됐음을 확인할 수 있었다. 문의가 실제 수정으로 바로 이어졌다.

다만 `Lcinfo`로 즉시 되돌리지는 않았다. 
문의 답변과 실측 확인을 마친 시점에 `ListInfo` 구현은 이미 동작·검증을 끝낸 상태였고 변경된지 얼마 안된 조회 조건이 안정적으로 유지되는지는 며칠 간 관찰이 필요하다고 보았다. 
또한 `ListInfo`만 제공하는 `dutyEmclsName`(응급의료기관 등급)·`dutyTel3`(응급실 직통 전화)는 우리 서비스에서 활용할 여지가 있다. 
복귀 여부는 캐싱 후속 이슈에서 성능 검증(전국 목록 약 7초 vs 좌표 조회)과 함께 판단한다.

## 교훈

1. **외부 서비스는 개발하려는 우리 서비스의 사용 시나리오로 검증한 뒤 채택한다** - 문서의 기능 설명은 그 API가 무엇을 하는지 알려줄 뿐, 우리 조건에서 어떻게 동작하는지는 알려주지 않는다. 이번 제약도 "24시간 운영되는 응급실을 밤에 조회한다"는 시나리오를 적용해서 테스트 했을 때 확인할 수 있었다. 외부 서비스 연동을 결정하기 전에 실제 사용 조건을 바탕으로 검증을 거쳐야 한다.
2. **외부 API 응답의 결측을 대비한다** - 공공데이터에는 필수처럼 보이는 필드(좌표)도 비어 있는 행이 섞인다. 원시 타입으로 받으면 한 건의 결측이 전체 파싱을 무너뜨리므로 래퍼 타입 + 필터링을 기본으로 한다.
3. **성능 관련 설정값은 실측으로 확정한다** — 활용가이드에는 9개 오퍼레이션 모두 "평균 응답 500ms"로 동일하게 적혀 있어 오퍼레이션별 실측값으로 보기 어려웠다. 실제 전국 목록 조회에 약 7초가 걸렸다. 이 차이가 간헐적 타임아웃을 낳았다. 문서에 기재된 값은 초기 기준으로 삼되 우리가 실제로 보내는 요청 조건/환경에서 측정해 최종값을 정해야 한다.
